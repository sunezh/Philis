General Implementation Advice

This section holds the cross-cutting engineering principles the Philis crates are built to. The advice here is deliberately language- and subsystem-agnostic: it explains why a pattern earns its place before any one crate adopts it. The shared utility crate is where these principles become reusable generics and macros — everything else consumes them.

Why data-oriented design matters for EDA tools

A layout engine is, at its core, a program that processes millions of geometric objects under tight geometric and electrical constraints. A modest analog block has 104–105 devices; the rectangles, polygons, via arrays, and routing segments that describe its physical realization can reach 106–107 objects. The placer, router, DRC checker, and extractor all sweep over subsets of these collections thousands of times per run.

At this scale, the dominant cost is not floating-point arithmetic — it is memory access. Every cache miss on a modern CPU stalls the pipeline for ~100 cycles (L1 hit ~4 cycles, DRAM ~200+ cycles). An inner loop that touches two fields of a 96-byte struct wastes 83% of every cache-line fetch. Multiply that by 106 elements and 103 iterations, and the wasted bandwidth dwarfs the useful computation.

Data-oriented design (DOD) is the discipline of organizing data structures so that the memory the CPU fetches is the memory the algorithm actually reads. The headline technique — struct-of-arrays (SoA) over array-of-structs (AoS) — splits a collection so that each field lives in its own contiguous array. A loop that reads only coordinates streams only coordinates; a loop that reads only net indices streams only net indices. The secondary techniques — indexes over pointers, encode-don't-store, bit-packing, padding elimination — shrink each element further, fitting more useful data per cache line.

The measured payoff is substantial. Andrew Kelley's Zig compiler refactor (Handmade Seattle, 2021) achieved 1.3×–3× wall-clock speedups from SoA and element-shrinking alone, with no algorithmic change. For Philis, where placement and routing are already the runtime bottleneck, this is not a micro-optimization — it is the single largest lever available before touching the algorithm.

How cache performance affects placement and routing runtime

Consider the concrete workload profile of a signoff-first placer:

  • Overlap / spacing (local DRC gate): reads bounding boxes (x, y, w, h) — 4 fields out of ~12 per device.
  • Equivalence check: reads device type, variant, orientation — 3 fields.
  • Intent satisfaction (symmetry / centroid): reads group ID, axis coordinate — 2 fields.
  • Wirelength estimation: reads net connectivity and terminal positions — a handful of fields from a different collection entirely.

In AoS layout, every gate fetches the full device record. In SoA layout, each gate streams only the fields it inspects. The cache- traffic reduction factor equals (total fields) / (fields used). For a 12-field device struct where a pass reads 3, that is a 4× reduction in memory bandwidth per pass. The optimizer may evaluate millions of candidates, and each candidate is checked against multiple gates. The savings compound.

The same pattern recurs in the router: net-segment collections are scanned for congestion, timing, and DRC feasibility, each reading a different field subset. And in the constraint compiler, rule tables are filtered by layer, by device type, and by rule family — three different access patterns on the same underlying collection.

The upshot: cache-aware data layout is not an afterthought for Philis; it is a first-class design axis, on par with algorithm selection and constraint modeling. The utility crate exists to make it cheap to adopt.

Why Rust

EDA tools have been written in C and C++ for decades, and newer projects have turned to Python. Philis is written in Rust for four concrete reasons:

  1. Ownership and borrowing as a design discipline. A layout engine's data flow is naturally a DAG of owned collections — the PDK owns technology records, the placer borrows them, the router borrows placer output. Rust's ownership model encodes this DAG in the type system. Aliasing bugs, use-after-free, and iterator invalidation — common sources of silent corruption in C++ EDA code — are compile-time errors in Rust. For a tool that must be correct (a misplaced rectangle is a silicon bug), eliminating these failure modes at compile time is worth more than any runtime check.

  2. No garbage-collector pauses. Python and Java EDA tools suffer GC pauses that are unpredictable and proportional to heap size. A layout engine's heap is large (the entire design lives in memory) and long-lived (the solver iterates for minutes). GC pauses during inner-loop iteration destroy cache locality and inject latency jitter. Rust's deterministic drop semantics mean memory is freed at scope exit, not at the GC's discretion, and the allocator never walks the heap to find garbage.

  3. Zero-cost abstractions for DOD. Rust's trait system, const generics, and monomorphization mean that a generic DataVec<T> compiles to the same machine code as a hand-rolled per-field array — there is no vtable, no boxing, no indirection penalty. The abstraction (a Vec-like API) is free at runtime; the specialization (SoA layout) is resolved at compile time.

  4. Proc macros for mechanical DOD transforms. The SoA split, padding elimination, index-width selection, and boolean-out-of-band extraction are all mechanical transforms on a struct's field list. Rust's procedural macro system lets utility implement these as #[derive(DataOptimize)] — the developer annotates a struct, and the macro emits the transformed storage with an identical API. This is the Rust analog of Zig's comptime reflection or Odin's #soa directive, adapted to Rust's token-level macro model.

Why not C++ (the traditional EDA language)?

C++ is the incumbent language for commercial EDA, and its performance ceiling is comparable to Rust's. The reasons Philis does not use it are ergonomic and safety-related, not performance-related:

  • Memory safety is manual. C++ has no ownership model. Aliasing, dangling pointers, iterator invalidation, and use-after-move are all legal programs that silently produce wrong results. In an EDA tool, a silent data corruption can propagate through placement and routing and surface only at silicon, where the cost of a bug is measured in months and millions of dollars. Rust eliminates these bug classes at compile time.
  • DOD generics require reflection that C++ lacks (until C++26). A generic SoA container needs to enumerate a struct's fields at compile time. C++ had no native way to do this until P2996 (adopted into the C++26 working draft in 2025, with partial compiler support). Before P2996, the options were X-macros, Boost.PFR on aggregates only, or hand-rolled tuple<vector<F>...>. Rust's proc macros have provided this capability since Rust 1.0 (2015).
  • Build-system complexity. C++ builds require a build system (CMake, Bazel, Meson), a package manager (Conan, vcpkg), and significant configuration per platform. Rust's cargo unifies building, testing, benchmarking, documentation, and dependency management in a single tool, with reproducible lockfiles. For a project that targets Rust + Python (via PyO3) + CLI, the reduction in build infrastructure is substantial.
  • Ecosystem for the Python bridge. Philis exposes a Python API via PyO3/Maturin, which provides zero-copy, type-safe bindings with automatic __init__/__repr__/__eq__ generation. The equivalent C++ path (pybind11) is mature but requires more boilerplate and has no ownership-model integration.

None of this means C++ EDA tools are bad — decades of proven commercial tools demonstrate otherwise. The argument is that for a new project starting today, Rust offers stronger correctness guarantees and better DOD tooling at the same performance level.

Why not Python-first (like ALIGN, MAGICAL)?

Several recent academic analog layout tools (ALIGN from Minnesota/Intel, MAGICAL from UT Austin) are written primarily in Python, with C++ acceleration for hot paths. This approach has real advantages: rapid prototyping, a large ecosystem of ML/optimization libraries (PyTorch, OR-Tools, scipy), and low barrier to entry for researchers.

Philis does not follow this path for three reasons:

  • Performance floor, not ceiling. A Python-first tool's inner loops are either pure Python (10–100× slower than native) or C++ extensions (which require crossing the FFI boundary per call and duplicating data structures across languages). Philis's placer and router are designed as tight iterative solvers where the inner loop is the entire program — there is no "glue code" that can afford to be slow.
  • GC pauses destroy cache locality. CPython's reference-counting GC (plus the cyclic collector) walks the heap at unpredictable intervals. For a layout engine whose working set is tens of megabytes of geometric data, these pauses evict hot cache lines and inject latency spikes that are invisible to profiling but real in wall-clock time.
  • DOD is impossible in Python. Python objects are heap-allocated, boxed, and pointer-chased. There is no way to lay out a million device records as contiguous SoA arrays in CPython — every object is a PyObject* with a refcount header. NumPy provides contiguous typed arrays, but only for numeric types, not for heterogeneous struct-of-arrays with mixed-type fields.

Philis instead provides a Python API as a thin facade over the Rust engine (via PyO3). The Python user gets the ergonomics of circuit.place_and_route() while the engine runs at native speed with native data layout. The Python layer is a caller, not an implementer.

Why not Zig (which has native DOD support)?

Zig is, in many ways, the ideal language for data-oriented design. Its comptime reflection gives the standard library enough information to ship MultiArrayList(T) — the exact SoA generic that Philis's DataVec aims to replicate. The DOD survey documents this in detail.

Philis does not use Zig for practical reasons:

  • Ecosystem maturity. Zig's package ecosystem is young. There is no equivalent of PyO3 for Python bindings, no mature GDSII/OASIS reader, no established SPICE parser, and no widely-used constraint solver bindings. Philis would need to write or port all of these from scratch.
  • Language stability. Zig has not reached 1.0. The standard library API changes between releases (the StructField.default_value → default_value_ptr rename is one example). Building a multi-year EDA project on a pre-1.0 language creates ongoing migration burden.
  • Safety model. Zig is safer than C but does not have Rust's ownership/borrowing system. Aliasing and use-after-free are runtime errors (via debug-mode safety checks), not compile-time errors. For a tool where correctness is paramount, Rust's compile-time guarantees are preferable.
  • Hiring and collaboration. Rust has a larger and more established community, more learning resources, and broader industry adoption. For a project that intends to attract contributors, the practical talent pool matters.

The DOD gap — Zig's comptime can observe field layouts while Rust's proc macros cannot — is real but bounded. The DOD page shows that Rust's proc-macro approach covers all the mechanical transforms (SoA split, field enumeration, index newtypes) and falls short only on layout-dependent decisions (size/alignment queries), which can be handled by annotations or profile-guided mode. The tradeoff is accepted.
