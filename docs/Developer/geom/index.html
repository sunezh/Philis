The Philis Geometry Kernel

Status: design reference. This section specifies the shared integer geometry kernel implemented in crates/geom (philis-geom). The crate is a dependency-free leaf of the workspace graph: both crates/place and crates/route depend on it, and crates/constraints may consume it for geometric predicates. See the implementation plan for build phases and method signatures.

The one-sentence thesis. Every shape, spatial query, boolean operation, and orientation transform in the Philis engine passes through one crate, using one coordinate system (i64 nanometers), with one set of invariants. There is no second geometry library.

Why a shared geometry kernel?

The placement engine and the routing engine both need axis-aligned rectangles, rectilinear polygons, spatial indices, boolean operations, and orientation transforms. Without a shared kernel, each crate builds its own — with its own conventions for winding order, containment semantics, degenerate-shape handling, and coordinate representation. The result is subtle bugs at the boundary: a rectangle that placement considers "touching" is "overlapping" to the router, or an orientation transform that placement applies about the bbox center while the router applies about the origin.

Extracting the kernel into crates/geom eliminates this class of bugs structurally. Both consumers operate on the same Rect, the same RectiPoly, the same Orientation enum, and the same GeometryStore. A containment check in the placement DRC oracle uses exactly the same code path as a containment check in the routing DRC engine.

The i64 coordinate decision

All geometry in the kernel uses i64 nanometers. There is no f64 anywhere in the crate. This is a deliberate restriction with three justifications:

  1. Exact arithmetic. Integer coordinates make equality, containment, and intersection tests exact. There are no epsilon comparisons, no tolerance parameters, no nearly_equal helpers. Two points are equal iff their coordinates are equal. Two rectangles overlap iff their intervals overlap. These are bit-exact predicates that compose transitively — if a == b and b == c, then a == c. Floating-point arithmetic does not guarantee this.
  2. No degenerate topology. Floating-point snap can produce degenerate polygons: zero-area slivers, self-intersecting edges, vertices that are "almost" collinear. These degeneracies propagate through boolean operations and spatial queries, producing corrupt geometry that is difficult to diagnose. Integer coordinates on a fixed grid cannot produce these degeneracies — every vertex is on-grid by construction.
  3. Determinism. Integer arithmetic is deterministic across platforms, compilers, and optimization levels. The same input always produces the same output, bit-for-bit. This is required for the certificate replay guarantee: given the same inputs, the engine must produce the same geometry, which must produce the same DRC results, which must produce the same certificate.
Range. An i64 nanometer coordinate can represent positions up to approximately +/- 9.2 billion meters. IC die sizes are on the order of millimeters (106 nm). Overflow is not a practical concern. The only operation that can approach the i64 boundary is area() on a very large rectangle (width * height), which the implementation guards with widening multiplication to i128.

The technology compiler (crates/tech) provides a db_unit_nm conversion factor for translating between internal nanometer coordinates and GDS database units at I/O time. All computation stays in nanometers; GDS conversion happens only at the read/write boundary.

Shape types

Rect — axis-aligned rectangle

The core shape. Axis-aligned, closed (boundary included), non-degenerate (x_lo < x_hi, y_lo < y_hi). This is the 95% shape in analog layout — every wire segment, every device bounding box, every DRC check region is a Rect. 

pub struct Rect {
    pub x_lo: i64,    // left edge (nm)
    pub y_lo: i64,    // bottom edge (nm)
    pub x_hi: i64,    // right edge (nm)
    pub y_hi: i64,    // top edge (nm)
}

impl Rect {
    pub fn new(x_lo: i64, y_lo: i64, x_hi: i64, y_hi: i64) -> Self;
    pub fn width(&self) -> i64;
    pub fn height(&self) -> i64;
    pub fn area(&self) -> i64;
    pub fn center(&self) -> Point;

    pub fn contains_point(&self, p: Point) -> bool;
    pub fn contains_rect(&self, other: &Rect) -> bool;
    pub fn overlaps(&self, other: &Rect) -> bool;

    pub fn intersection(&self, other: &Rect) -> Option<Rect>;
    pub fn expand(&self, dx: i64, dy: i64) -> Rect;
    pub fn manhattan_distance(&self, other: &Rect) -> i64;
    pub fn bounding_union(&self, other: &Rect) -> Rect;
    pub fn translate(&self, dx: i64, dy: i64) -> Rect;
}

The constructor enforces the non-degeneracy invariant: zero-width or zero-height rectangles are rejected because they create ambiguous containment semantics and degenerate spatial-index entries. Rect is Copy, 32 bytes, and fits in half a cache line with no pointer chasing.

RectiPoly — rectilinear polygon

A polygon where every edge is axis-aligned — L-shapes, T-shapes, U-shapes, and the min-area patches that DRC rules sometimes require. Vertices are stored in counter-clockwise (CCW) order. The first vertex is not repeated at the end. 

pub struct RectiPoly {
    vertices: Vec<Point>,     // CCW, >= 4 vertices, all edges axis-aligned
}

impl RectiPoly {
    pub fn new(vertices: Vec<Point>) -> Result<Self, GeomError>;
    pub fn bounding_box(&self) -> Rect;
    pub fn contains(&self, p: Point) -> bool;
    pub fn area(&self) -> i64;
    pub fn decompose(&self) -> Vec<Rect>;
    pub fn edges(&self) -> impl Iterator<Item = (Point, Point)> + '_;
}

The constructor validates three invariants: all edges are axis-aligned, the winding is CCW (CW input is reversed automatically), and the polygon is simple (non-self-intersecting). decompose() breaks the polygon into non-overlapping axis-aligned rectangles using a horizontal-sweep maximal-strip algorithm, enabling spatial-index insertion and DRC checking on arbitrary rectilinear shapes.

No arbitrary polygons. 45-degree and freeform geometry is out of scope. Routing and placement geometry in analog CMOS is overwhelmingly rectilinear. If RF routing eventually demands angled geometry, it will be added as a separate shape type — the existing rectilinear types will not be polluted with angle-handling complexity.

Spatial index architecture

Layer-per-index R-tree

The spatial index uses a one-R-tree-per-layer architecture, backed by the rstar crate. This granularity is chosen for three reasons:

  1. DRC rules are intra-layer or adjacent-layer. A minimum-spacing check on metal1 only needs metal1 shapes. Querying a single-layer index returns no cross-layer noise and avoids post-filtering.
  2. Per-layer shape counts are manageable. A typical analog block has thousands of shapes per layer, not millions. A single R-tree per layer stays cache-friendly and has fast query times.
  3. Layer iteration is natural. Many operations sweep layer by layer (DRC, extraction, GDS output). Per-layer indices align with this pattern.

The index is behind a SpatialIndex trait so the backend can be swapped without touching callers: 

pub trait SpatialIndex: Send + Sync {
    fn insert(&mut self, shape: ShapeRef);
    fn remove(&mut self, id: ShapeId) -> bool;
    fn query_point(&self, point: Point) -> Vec<&ShapeRef>;
    fn query_window(&self, rect: &Rect) -> Vec<&ShapeRef>;
    fn query_nearest(&self, point: Point, k: usize) -> Vec<&ShapeRef>;
    fn len(&self) -> usize;
    fn is_empty(&self) -> bool;
}

The GeometryStore

GeometryStore is the top-level container that routes all geometry operations through the per-layer spatial indices. It owns the monotonic ShapeId allocator and a secondary owner-to-shapes index for ownership queries. 

pub struct GeometryStore {
    layers: BTreeMap<LayerId, RTreeIndex>,
    next_id: u64,
    owner_index: BTreeMap<ShapeOwner, Vec<ShapeId>>,
}

impl GeometryStore {
    pub fn insert(&mut self, layer: LayerId, owner: ShapeOwner,
                  geometry: ShapeGeometry) -> ShapeId;
    pub fn remove(&mut self, id: ShapeId) -> bool;

    pub fn query_point(&self, layer: LayerId, point: Point)
        -> Vec<&ShapeRef>;
    pub fn query_window(&self, layer: LayerId, rect: &Rect)
        -> Vec<&ShapeRef>;
    pub fn query_within_distance(&self, layer: LayerId, rect: &Rect,
                                 distance: i64) -> Vec<&ShapeRef>;
    pub fn shapes_of(&self, owner: ShapeOwner) -> Vec<&ShapeRef>;
}

Key properties:

  • Monotonic IDs. ShapeId values only increase. An ID is never reused after remove, even if the slot is logically free. This prevents dangling-reference bugs where a stale ID resolves to a different shape after rip-up and re-route.
  • Owner index. A secondary BTreeMap<ShapeOwner, Vec<ShapeId>> enables shapes_of(Net(id)) queries without scanning every layer. This is used by the routing state's ownership map and by the LVS connectivity checker.
  • Deterministic iteration. BTreeMap is used everywhere instead of HashMap. Iteration order is sorted by key, which is required for deterministic certificate replay.
  • Lazy layer creation. A layer index is created on first insertion. Querying a layer that has never had a shape returns an empty result, not an error.
query_within_distance is not a radius search. It dilates the query rectangle by distance on each side and queries the expanded window, then post-filters by actual Manhattan distance between the query rect and each result's bounding box. This is the correct semantic for DRC spacing checks: "find all shapes whose edge-to-edge distance from this shape is less than d."

ShapeRef — shapes with ownership metadata

A ShapeRef is the unit of storage in the spatial index. It pairs a geometric shape with the metadata that consumers need for DRC, LVS, and ownership tracking: 

pub struct ShapeRef {
    pub id: ShapeId,              // monotonic, never-reused
    pub layer: LayerId,           // which layer this shape lives on
    pub owner: ShapeOwner,        // Net(id) | Obstacle | Pin(id) | Fill | Shield(id)
    pub bbox: Rect,               // cached bounding box (R-tree envelope)
    pub geometry: ShapeGeometry,  // Rect(Rect) | Poly(RectiPoly)
}

pub enum ShapeOwner {
    Net(NetId),
    Obstacle,
    Pin(TerminalId),
    Fill,
    Shield(NetId),
}

pub enum ShapeGeometry {
    Rect(Rect),
    Poly(RectiPoly),
}

The bbox field is the R-tree envelope and is always equal to geometry.bounding_box(). The store enforces this at insertion time. The owner field carries enough information for DRC to distinguish same-net from different-net pairs, for LVS to track connectivity, and for the routing state to map shapes back to their owning nets.

Orientation transforms

IC layout uses eight standard orientations, forming the dihedral group D4. The kernel provides a closed Orientation enum with transform methods:

MXR90yxMX then R90

pub enum Orientation {
    R0, R90, R180, R270, MX, MY, MXR90, MYR90,
}

impl Orientation {
    pub fn apply_point(self, p: Point) -> Point;
    pub fn apply_rect(self, r: Rect) -> Rect;
    pub fn apply_about(self, p: Point, center: Point) -> Point;
    pub fn apply_poly(self, poly: &RectiPoly, center: Point) -> RectiPoly;
    pub fn inverse(self) -> Orientation;
    pub fn compose(self, other: Orientation) -> Orientation;
    pub fn is_reflected(self) -> bool;
}

apply_about is the method consumers typically call: it transforms a point relative to a center (the device's bounding-box center for placement, the cell origin for GDS output). Internally it translates to the origin, applies the orientation, and translates back.

The placement engine uses MY as the default mirror for symmetric pairs (reflection about the vertical center axis). The constraint compiler determines which mirror operation a Symmetric constraint implies based on the symmetry-axis direction and maps it to the appropriate Orientation variant.

Group closure. The eight orientations are closed under compose — composing any two orientations produces another member of the set. inverse is its own inverse: o.compose(o.inverse()) == R0 for all o. The implementation verifies this with an exhaustive test over all 64 compose pairs.

Boolean operations

Three boolean operations are provided: merge (union), clip (intersection), and difference. Each has a rect-rect fast path and a general scanline sweep for rectilinear regions.

Rect-rect fast path

Most boolean operations in both placement and routing involve two rectangles. The fast path handles these with direct coordinate comparisons and no heap allocation (for intersection) or minimal allocation (at most 3-4 output rects for union/difference):

  • rect_intersect(a, b) -> Option<Rect> — trivial: max(a.x_lo, b.x_lo), min(a.x_hi, b.x_hi), etc. Returns None if the result would be degenerate.
  • rect_union(a, b) -> BooleanResult — if overlapping, decomposes into at most 3 non-overlapping rects. If disjoint, returns both as-is.
  • rect_difference(a, b) -> BooleanResult — subtracts b from a, producing at most 4 non-overlapping rects.

General scanline sweep

For multi-rect or RectiPoly operands, the kernel uses a y-coordinate sweep:

  1. Collect all unique y-coordinates from both operand sets as sweep events.
  2. Sort events. Between consecutive y-values, the cross-section is a set of horizontal intervals.
  3. Apply the boolean operation (union/intersection/difference) to the interval sets using a sorted-interval merge algorithm.
  4. Reconstruct the result as a set of maximal-height axis-aligned rectangles.

Complexity: O((n + k) log n) where n is the total vertex count and k is the number of intersection events. For the shapes analog layout produces (typically fewer than 20 vertices per polygon), this is fast.

Who consumes this crate

The placement engine (crates/place)

Placement uses the geometry kernel for:

  • Device bounding boxes. The primitive catalog stores each device template as a Rect at origin. Rect::bounding_union computes the overall bbox.
  • Overlap checks. The SA cost function calls Rect::overlaps to detect device-device overlaps.
  • DRC spacing. The placement DRC oracle uses Rect::manhattan_distance and GeometryStore::query_within_distance to check minimum spacing rules between placed devices.
  • Device R-tree. The SA solver maintains a GeometryStore for fast neighbor queries during move evaluation.
  • Orientation transforms. GDS polygon emission applies Orientation::apply_rect and apply_poly to each device's template geometry at its placed position and orientation.

The routing engine (crates/route)

Routing uses the geometry kernel for:

  • Wire shape management. Every committed wire segment is inserted into the GeometryStore via insert. Rip-up removes it via remove.
  • DRC check regions. After each commit, the incremental DRC engine queries GeometryStore::query_window on the affected region (dilated by r_max) to find shapes that may violate spacing rules.
  • Boolean ops for region clipping. difference(routing_region, obstacles) computes the legal routing space. merge(net_shapes) combines overlapping same-net shapes for LVS connectivity.
  • Net ownership. GeometryStore::shapes_of(Net(id)) returns all shapes belonging to a net, used by the routing state's ownership map.

The constraints compiler (crates/constraints)

Constraints uses the kernel for geometric predicates: guard-ring enclosure checks (Rect::contains_rect), spacing verification (Rect::manhattan_distance), and symmetry-axis mirror geometry (Orientation::apply_about).

Corner stitching (future option)

The R-tree answers "what shapes are here?" efficiently. It does not answer "what is the largest empty rectangle containing this point?" — that requires either a separate computation or a fundamentally different data structure.

Corner stitching tiles the entire plane with non-overlapping rectangles, including explicit space tiles for empty regions. This makes empty-space queries nearly free: the space tile at a point is the answer. This matters for the routing access oracle ("find a legal landing pad here") and the detailed router ("find a legal jog here").

The cost is significant: corner stitching is approximately 5x the implementation complexity of an R-tree wrapper. Insert and remove require "stitch surgery" to split and merge tiles while maintaining the maximal-horizontal-strip invariant. No standard Rust crate provides it; it must be implemented from scratch.

The decision: use the R-tree through Phase 2. If profiling shows that empty-space queries are a bottleneck in Phase 3 (specifically in the access oracle and detailed router), implement corner stitching as an alternative SpatialIndex backend. The trait boundary means the switch is local to the index module — no consumer code changes.

Do not implement speculatively. Corner stitching is a known-good data structure for VLSI layout tools (Magic, KLayout internals). But it is a large engineering investment and its benefit depends on the query mix. The trait boundary is the insurance policy: it costs nothing now and makes the switch possible later.

Dependencies

The geometry kernel is a leaf crate with minimal dependencies:

CrateVersionPurpose
rstar 0.12 R-tree spatial index with native i64 coordinate support

No floating-point geometry crates (geo, parry2d), no serialization (serde), no intra-workspace dependencies. The kernel is self-contained.

Soundness boundary. The geometry kernel provides correct shapes, correct spatial queries, and correct boolean operations. It does not provide DRC rule semantics (which spacing applies to which layer pair), technology interpretation (what a layer means electrically), or signoff guarantees. Those belong to the technology compiler, the DRC engine, and the constraint certificate, respectively. The kernel is infrastructure — it makes those higher-level systems possible, but it is not a substitute for them.
