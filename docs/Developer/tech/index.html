The Philis Technology Compiler

Status: design reference. This section specifies the philis-tech crate (crates/tech), the shared PDK technology compiler that all three engine crates depend on. The crate is scaffolded with its Cargo.toml and stub lib.rs in place. Nothing beyond the scaffold is implemented yet — see Implementation status.

The one-sentence thesis. A place-and-route engine that cannot answer "what are the spacing rules on metal 2?" without importing a proprietary deck is not portable. A shared, compiled technology model with honest coverage classification makes the engine PDK-agnostic and the certificate auditable.

Why the technology model is shared

All three engine crates need compiled PDK data, and each was planning to build its own:

  • Constraints had a technology/ module with a CompiledTechnology trait + SKY130 concrete, coverage inventory, and MCMM-keyed rule predicates.
  • Place had a pdk/ module with a PDK compiler, LayerInfo, spacing/width/enclosure rules, well rules, orientations, row pitch, and a coverage report.
  • Route had a tech/ module with the full seven-tuple technology model T = (L, G, V, R, E, X, M), a two-stage compiler pipeline, and the Philis-native PDK schema.

Three independent technology models mean three independent sets of layer definitions, three sets of spacing rules, three coverage inventories. When the PDK changes, three modules must be updated. When a rule predicate has a bug, three consumers have different answers to the same question. When the certificate records a pdk_oracle_hash, which of the three hashes does it use?

The philis-tech crate eliminates this by extracting the shared technology model into a single crate that all three consumers depend on. Each consumer gets a &CompiledTech reference to the same immutable, compiled structure. The hash is computed once and used everywhere.

The two-stage pipeline

The technology compiler uses a two-stage pipeline that separates format-specific import from format-agnostic compilation: 

  External PDK files              Philis-native schema          CompiledTech
  (LEF, Sky130 files,     ---->   (JSON file on disk      ---->  (in-memory,
   hand-authored JSON)             or in-memory)                  immutable)

        IMPORT                          COMPILE
    (format-specific)              (format-agnostic)

Stage 1: Import

A format-specific importer reads external PDK files and produces a Philis-native JSON schema. The importer is responsible for mapping external layer names, rule formats, and parameter conventions into the Philis schema vocabulary. The user can inspect and edit the resulting JSON before compilation.

Three importers are planned:

ImporterInputCoverage
LEF (generic) Technology LEF file Layer/via/site definitions. No parasitics, antenna, or density.
SKY130 (targeted) Hardcoded data from the open-source SKY130 PDK Layers, vias, spacing/width/enclosure, extraction parameters. The most complete importer.
JSON (passthrough) Hand-authored JSON schema Whatever the user provides. Coverage annotations are explicit.

Stage 2: Compile

The compiler reads the Philis schema and builds an immutable CompiledTech structure. It validates structural invariants, classifies rule coverage, derives the PdkState, and computes the BLAKE3 PDK hash.

The compiler never sees the original external files. This means:

  • New PDK formats are supported by writing a new importer, not touching the compiler.
  • Users can hand-write or hand-edit the schema for unsupported PDKs.
  • The schema is version-controlled and diffable.
  • The compiler can be tested independently of any external PDK format.
Why two stages instead of one? A single-stage pipeline that reads LEF directly into a compiled structure couples the compiler to the LEF format. When a second format appears (Sky130 file tree, IHP SG13G2, commercial TechFile), the compiler must grow a second parser. The two-stage design means the compiler has exactly one input format (the Philis schema), and format diversity is handled entirely in the import stage.

The CompiledTech data model

CompiledTech is the immutable, compiled oracle that every downstream crate queries. It is Send + Sync — safe to share across threads via &CompiledTech. It is constructed once and never mutated. 

pub struct CompiledTech {
    name: String,
    db_unit_nm: i64,
    manufacturing_grid_nm: i64,
    layers: LayerStack,
    vias: ViaTable,
    grids: GridTable,
    rules: RuleSet,
    extract: ExtractModel,
    coverage_report: RuleCoverageReport,
    pdk_state: PdkState,
    pdk_hash: [u8; 32],   // BLAKE3
}

Each sub-structure owns a specific domain of the compiled technology. Consumers access them through typed accessors on CompiledTech:

Sub-structureWhat it ownsPrimary consumers
LayerStack Ordered layer definitions (bottom to top), name-to-id lookup, layer class and direction All three: constraints (rule references), place (layer roles), route (stack traversal)
ViaTable Via definitions indexed by layer pair, cut size, enclosure, resistance Route (via selection, via arrays), place (via enclosure for DRC)
GridTable Per-layer track positions (pitch + offset), preferred direction, width bounds Route (track assignment), place (row pitch, site width)
RuleSet All DRC predicates with typed dispatch methods All three: constraints (rule IDs for coverage), place (DRC oracle), route (geometry legality)
ExtractModel Per-corner extraction parameters: sheet R, area/fringe cap, coupling cap, via R Route (in-loop PEX surrogate), constraints (parasitic budget checking)

Layer stacks and via definitions

LayerStack

The layer stack is an ordered sequence of layer definitions, sorted from bottom (substrate) to top (passivation). Each layer carries:

  • A stable LayerId (an index into the vector) for O(1) random access.
  • A GDS layer/datatype pair for physical layout correspondence.
  • A LayerClass that classifies its functional role.
  • A LayerDirection (Horizontal, Vertical, or Any) for routing layers.
  • Dimensional constraints: minimum width, maximum width (if any), thickness.
pub enum LayerClass {
    Diffusion,
    Poly,
    LocalInterconnect,
    Metal(u8),       // Metal(1) = M1, Metal(2) = M2, ...
    Via(u8),         // Via(1) = V1 (M1-M2), Via(2) = V2 (M2-M3), ...
    Well,            // nwell, pwell, dnwell
    Implant,         // nsdm, psdm, hvtp, lvtn
    Marker,
    Keepout,
    Pad,
    Passivation,
}

pub enum LayerDirection {
    Horizontal,
    Vertical,
    Any,
}

The LayerStack provides name-to-id lookup via a BTreeMap (deterministic iteration order, important for hashing) and filtered iterators for routing layers, metals, and vias.

ViaTable

The via table indexes all legal via transitions by (bottom_layer, top_layer). Multiple via definitions per layer pair are supported — different cut sizes, enclosures, or array rules for the same layer transition. Each ViaDef carries:

  • A stable ViaId for fast reference.
  • Bottom and top LayerIds.
  • Cut size (width, height in nm).
  • Cut spacing for via arrays.
  • Asymmetric enclosure requirements for bottom and top layers ([x_enc, y_enc]).
  • Via resistance (ohms per cut).

GridTable

The grid table provides per-layer track positions for routing. Each routing layer has a GridDef with pitch, offset, direction, and width bounds. The grid table supports:

  • track_center(layer, index) — compute the center coordinate of track index on the given layer.
  • snap_to_track(layer, coord) — snap an arbitrary coordinate to the nearest legal track.
  • tracks_in_range(layer, lo, hi) — enumerate all track positions within a coordinate range.

DRC rule predicates

The RuleSet stores all DRC predicates and provides typed dispatch methods that return the strictest applicable value for a given query. This is the primary interface consumers use for geometry legality checks.

Dispatch methods

impl RuleSet {
    /// Strictest applicable spacing for the layer, considering
    /// both shapes' widths. Handles base, width-dependent, and
    /// same-net spacing rules.
    pub fn min_spacing(&self, layer: LayerId, width_a: i64, width_b: i64) -> i64;

    /// Minimum legal width for the layer.
    pub fn min_width(&self, layer: LayerId) -> i64;

    /// Enclosure of a via on the given layer: [x_enc, y_enc].
    pub fn via_enclosure(&self, via: ViaId, layer: LayerId) -> [i64; 2];

    /// Minimum area for the layer, if constrained.
    pub fn min_area(&self, layer: LayerId) -> Option<i64>;

    /// End-of-line spacing for the layer and given EOL width.
    pub fn eol_spacing(&self, layer: LayerId, width: i64) -> Option<i64>;

    /// Spacing considering parallel run length.
    pub fn prl_spacing(&self, layer: LayerId, width: i64, prl: i64) -> i64;
}

Width-dependent spacing

Many PDKs define spacing rules that depend on the width of the adjacent shapes. A typical rule reads: "if either shape is wider than 3000 nm, spacing must be at least 280 nm (instead of the base 140 nm)." The dispatch method finds the rule whose width_threshold_nm is the largest value less than or equal to max(width_a, width_b). If no width-dependent rule matches, the base (unconditional) spacing is returned.

Per-predicate coverage

Every rule in the RuleSet carries a Coverage classification. This tells consumers — and ultimately the certificate — whether the rule was fully coded, partially coded, approximate, external-only, or missing. The constraints crate uses this to build its coverage inventory; the place and route crates use it to annotate their certificates.

Extraction parameters

The ExtractModel provides per-corner parasitic extraction parameters for in-loop PEX surrogates and parasitic budget checking. All parameters are keyed by PVT corner (e.g., "tt", "ss", "ff"), with a designated default corner for in-loop estimates.

ParameterUnitWhat it models
Sheet resistance ohm/sq Wire resistance per layer. Dominates IR drop and RC delay.
Area capacitance fF/um2 Parallel-plate capacitance between a wire and the substrate/adjacent layer.
Fringe capacitance fF/um Edge-field capacitance per unit wire length. Dominates for narrow wires.
Coupling capacitance fF/um Capacitive coupling between adjacent wires on the same or neighboring layers. The coupling window (nm) defines the interaction range.
Via resistance ohm/cut Resistance per via cut. Multiple cuts reduce the effective resistance proportionally.

The route crate's in-loop PEX surrogate uses the default corner for fast wire-resistance and capacitance estimates during search. The constraints crate uses the extraction model to check parasitic budgets against bounded obligations. Full multi-corner analysis is a signoff feature — the in-loop surrogate uses a single corner for speed.

Accuracy vs. speed. The extraction model in philis-tech provides first-order parasitic estimates suitable for in-loop decision-making. It is not a replacement for a calibrated field solver (Calibre xRC, StarRC). The honest coverage model classifies extraction accuracy: Coded for parameters directly from the PDK, Approximate for parameters with known accuracy limitations. The certificate records which extraction corner was used and at what confidence level.

Coverage classification and PdkState

Every rule predicate in the compiled technology carries a Coverage classification — a nine-variant enum that tells the engine and the certificate exactly how much confidence to place in that rule:

CoverageMeaning
Coded Fully coded with an internal predicate. The engine can check and prove compliance.
Partial Some conditions checked internally; others need external verification.
Approximate Coded but with known accuracy limitations (e.g., EM models with approximate current estimates).
ExternalOnly Can only be checked by an external signoff deck. The engine records the obligation but cannot prove it.
ManualReview Requires human review. No machine-checkable predicate exists.
Missing Known to exist for this node but not modeled at all.
NotApplicable Not applicable to this node (e.g., multipatterning on a mature single-patterning process).
Contradictory Two or more sources provide conflicting data for this rule.
Unsupported Rule class is known but no predicate exists in the engine.

The coverage values form a lattice ordered from best (Coded) to worst (Contradictory, Unsupported). The lattice meet operation returns the worse of two values, which means merging coverage across multiple rules is conservative: a set of rules is only Coded if every member is Coded.

PdkState derivation

After classifying all predicates, the compiler derives the overall PdkState — a four-variant enum that summarizes the PDK's readiness for the engine:

PdkStateConditionWhat it means
FullSignoff All required rules are Coded. Full signoff confidence. The engine can prove every required rule.
AbstractComplete Most required rules are at least Partial. Abstract placement and routing are possible with known gaps.
SparseResearch Some required rules are present but coverage is sparse. Research and prototyping only. Not for tapeout.
ContradictoryOrMissing At least one required rule is Missing or Contradictory. The compiled technology may produce incorrect results. Proceed with extreme caution.

"Required" rules are the minimum set without which the engine cannot produce legal geometry: basic spacing and width for each routing layer, via enclosure for each via in the stack, and connectivity extraction parameters (sheet resistance) for each routing layer.

The RuleCoverageReport

The RuleCoverageReport counts predicates per coverage bucket. It travels with every certificate so the consumer knows exactly what was proven and what was not: 

pub struct RuleCoverageReport {
    pub coded: u32,
    pub partial: u32,
    pub approximate: u32,
    pub external_only: u32,
    pub manual_review: u32,
    pub missing: u32,
    pub not_applicable: u32,
    pub contradictory: u32,
    pub unsupported: u32,
    pub total: u32,
}
Missing is not "no rule." A Missing classification means the rule is known to exist for this process node but is not modeled in the compiled technology. This is fundamentally different from "the rule does not exist." A layout that passes all Coded checks but has Missing rules is not DRC-clean — it has unchecked rules. The certificate records this distinction, and the PdkState degrades accordingly.

The Philis-native PDK schema

The Philis PDK schema is a JSON document that captures the routing-relevant subset of a PDK. It is the interchange format between importers and the compiler, and is designed to be:

  • Human-readable. A layout engineer can open the JSON in a text editor, understand what rules are encoded, and verify them against the PDK documentation.
  • Hand-editable. For PDKs without an automated importer, users can author the schema manually. Coverage annotations let the user honestly declare what they know.
  • Diffable. Schema changes between PDK revisions produce clean diffs.
  • Version-controlled. The schema has a schema_version field. The compiler rejects schemas with incompatible major versions.

A minimal schema for a two-metal process looks like this: 

{
  "schema_version": "1.0",
  "name": "example_2metal",
  "node_family": "demo",
  "db_unit_nm": 1,
  "manufacturing_grid_nm": 5,

  "layers": [
    {
      "name": "met1", "gds_layer": 68, "gds_datatype": 20,
      "class": "metal", "class_index": 1,
      "direction": "horizontal",
      "pitch_nm": 340, "offset_nm": 170,
      "min_width_nm": 140
    },
    {
      "name": "met2", "gds_layer": 69, "gds_datatype": 20,
      "class": "metal", "class_index": 2,
      "direction": "vertical",
      "pitch_nm": 340, "offset_nm": 170,
      "min_width_nm": 140
    }
  ],

  "vias": [
    {
      "name": "via1", "bottom": "met1", "top": "met2",
      "cut_size_nm": [150, 150], "cut_spacing_nm": [170, 170],
      "enclosure_bottom_nm": [55, 85],
      "enclosure_top_nm": [55, 85],
      "resistance_ohm": 4.5, "coverage": "coded"
    }

    { "name": "m1.S.1", "layer": "met1",
      "min_spacing_nm": 140, "coverage": "coded" },

The full schema specification — including extraction parameters, enclosure rules, area rules, EOL rules, EM rules, and antenna rules — is documented in the implementation plan.

Hot-switchability

The technology compiler is designed for hot-switchable PDK backends. New PDK = new importer. Consumers never change.

The contract between the tech crate and its consumers is the CompiledTech structure and its typed accessors. A consumer that calls tech.rules().min_spacing(layer, w1, w2) does not know or care whether the underlying data came from a LEF file, a hardcoded SKY130 importer, or a hand-authored JSON schema. The same query works the same way regardless of the PDK backend.

The planned PDK progression:

PDKNodeImporterStatus
SKY130 130nm planar CMOS Hardcoded data + targeted importer First target. Hardcoded data in progress.
IHP SG13G2 130nm SiGe BiCMOS Targeted importer (similar structure to SKY130) Second target. Validates PDK-agnosticism.
Generic LEF Any node with a Technology LEF Generic LEF parser Third target. Covers commercial PDKs (with gaps).

When the IHP SG13G2 importer is written, the LayerClass enum may need extension (e.g., for bipolar devices), but the CompiledTech structure, the RuleSet dispatch methods, and the ExtractModel accessors remain unchanged. This is the proof that the abstraction is correct: a different process node produces a different CompiledTech with different data, but the same interface.

The importer is not the compiler. Adding a new PDK means writing a new importer (a few hundred lines that map the PDK's file structure into the Philis schema). It does not mean touching the compiler, the schema spec, the validation logic, or any consumer crate. The two-stage pipeline makes this possible: the compiler's only input is the schema, and the schema is the same regardless of which importer produced it.

PDK hashing for certificates

The compiled technology is hashable. The BLAKE3 hash covers all data that affects the compiled structure: layer definitions, via definitions, all DRC rules, extraction parameters, coverage classifications, and the derived PdkState. The hash is computed once at construction time and stored in CompiledTech.pdk_hash.

This hash participates in the constraint certificate (ConstraintCertificate.pdk_oracle_hash) and the route certificate (RouteCertificate.pdk_oracle_hash). Any change to the compiled technology produces a different hash, invalidating all cached results. A third party can re-import the same PDK data, recompile, and verify that the hash matches — which is the precondition for certificate replay.

Stability invariant

Same input data must produce the same hash across Rust compiler versions, platforms, and runs. This requires:

  • Deterministic iteration order (BTreeMap, not HashMap, or sorted Vec).
  • Canonical byte encoding (little-endian for integers, UTF-8 for strings).
  • Floating-point values hashed as their to_le_bytes() representation (bit-exact, not value-exact).

What each consumer needs

The three consumer crates depend on philis-tech for different subsets of the compiled technology:

ConsumerSub-structures usedKey queries
Constraints Full CompiledTech, Coverage, PdkState, RuleCoverageReport Coverage inventory for the ConstraintCertificate, rule IDs for the IntentGraph, pdk_hash() for certificate binding
Place LayerStack, GridTable, RuleSet min_spacing(), min_width(), via_enclosure() for the DRC oracle; grid pitch and offset for row/site computation; pdk_hash()
Route LayerStack, ViaTable, GridTable, RuleSet, ExtractModel All dispatch methods for geometry legality; ExtractModel for in-loop PEX surrogate (wire R, cap, coupling, via R); pdk_hash()
No consumer modifies the technology. Consumers receive &CompiledTech. There is no mutable access, no interior mutability, and no way for a consumer to inject data back into the compiled technology. If the PDK changes, the entire CompiledTech is rebuilt from scratch and every downstream result is invalidated. This is the "whole certificate invalidation" property: a PDK change invalidates everything, and the hash proves it.

The SKY130 concrete implementation

SKY130 is the first concrete PDK target. It is an open-source 130nm planar CMOS process from SkyWater Technology, widely used in academic and open-source IC design. The open PDK provides enough data for a useful (though incomplete) CompiledTech.

Layer stack

SKY130 provides one local interconnect layer (li1), five metal layers (met1 through met5), and a full set of vias connecting them. The lower metals (met1, met2) have fine pitch (340 nm) suitable for signal routing; the upper metals (met3, met4) have coarser pitch (680 nm) for power and buses; met5 is a thick top metal for power distribution.

Alternatives considered

Why not parse the DRC deck directly instead of a two-stage pipeline?

Foundry DRC decks (Calibre SVRF, Mentor Calibre DRC, KLayout .lydrc) are procedural programs, not declarative rule sets. A Calibre DRC file for a modern node can exceed 100,000 lines of SVRF code with conditional logic, derived layers, density-computed layers, and multi-step operations. Parsing this into a structured rule set is a research project in its own right — and the result would be coupled to a specific DRC format.

The two-stage pipeline sidesteps this entirely. The importer extracts what it can from whatever source is available (LEF, PDK documentation, hand transcription). The compiler works with the structured Philis schema. Rules that the importer cannot extract are classified as Missing or ExternalOnly — the coverage model makes the gap explicit rather than pretending it does not exist.

This is the honest approach: a technology model that claims to have every rule but silently drops the ones it could not parse is more dangerous than one that says "I have 40 of 200 rules, here is what is missing."

Why not use a trait object instead of a concrete CompiledTech?

The constraints crate's original design used a CompiledTechnology trait with a SKY130 concrete implementation. This makes PDK-switching a matter of swapping the trait implementor. But it introduces three costs:

  1. Virtual dispatch on every rule query. The route crate calls min_spacing() millions of times during search. A virtual call adds an indirect branch prediction miss on every query. With a concrete struct, the compiler inlines the lookup.
  2. Heterogeneous data behind a uniform interface. Different PDKs have different layer counts, different rule structures, different extraction models. A trait forces every implementor to present the same interface, which means either the interface is too narrow (losing PDK-specific data) or too wide (every implementor must provide methods it does not need).
  3. The import/compile split already provides PDK-agnosticism. The compiler produces the same CompiledTech struct regardless of which importer produced the schema. The struct is the PDK-portability boundary. A trait adds a second portability boundary on top, with no additional benefit.

The chosen design uses a concrete CompiledTech struct. PDK-switching happens at the import stage (different importer -> different schema -> same struct). The compiled structure is the same type regardless of the PDK, which means consumers can be generic over PDK without trait objects or type parameters.

Why not let each consumer maintain its own technology model?

This is the status quo. Each consumer crate was building its own technology model with its own layer definitions, spacing rules, and coverage tracking. The problems are:

  • Consistency. Three independent spacing rule implementations mean three chances to transcribe the wrong value. If the placer thinks M1 spacing is 140 nm and the router thinks it is 130 nm, the placer produces geometry that the router considers illegal. This bug is silent and extremely difficult to find.
  • Maintenance. When the PDK changes or a bug is found, three modules must be updated. With a shared crate, one fix propagates to all consumers.
  • Certificate coherence. The constraint certificate and route certificate each record a pdk_oracle_hash. If the three consumers have different technology data, the hashes are different, and the certificates are not comparable.

A single shared crate eliminates all three problems. The cost is a new dependency in the workspace, but the crate has minimal dependencies of its own (philis-geom, serde, blake3) and adds no coupling between consumers.

Why BLAKE3 instead of SHA-256 or a simpler hash?

The PDK hash is computed once at compilation time and stored for certificate binding. Speed is not the primary concern — the technology data is small (a few KB). The choice of BLAKE3 is based on:

  • Determinism. BLAKE3 produces identical output across platforms and compiler versions for identical input. SHA-256 does too, but BLAKE3's Rust crate (blake3) is well-maintained and widely used in the Rust ecosystem.
  • Collision resistance. 256-bit output provides sufficient collision resistance for certificate binding. No one is going to craft a collision to fake a PDK hash.
  • Ecosystem alignment. BLAKE3 is the hash used by Cargo, rustup, and many other Rust tools. Using the same hash avoids adding a separate crypto dependency.

A simpler hash (FNV, CRC32) would not provide collision resistance. SHA-256 would work but adds a separate dependency when BLAKE3 is already in the ecosystem.

Soundness boundary. The technology compiler cannot make a PDK correct. Its job is to encode the rules it has access to, classify what it does not have, and make the coverage explicit in every certificate. A CompiledTech with PdkState::SparseResearch is useful for development and prototyping — but it is not a substitute for a foundry-qualified signoff deck. The certificate must always say which.
