Canonical Model & Identity

Everything downstream rests on three closed vocabularies — the obligation class, the coverage value, and the constraint tuple — plus one deterministic identity scheme. They are owned here and reused, never redefined, by placement, routing, and analysis.

Obligation class — how the design treats it

The class is a closed seven-variant enum. Extending it is an additive, coordinated change to this single owner — never a per-consumer local addition, because that is the only way projection soundness can hold across stages. 

ObligationClass =
  Hard | Joint | Bounded | Soft | Unsupported | ExternalOnly | ManualReview
VariantMeaning
Harda violation makes the candidate unacceptable.
Jointmembers must be solved or repaired together — a global constraint (a common-centroid array, an interdigitated bank, a differential pair). Joint feasibility cannot be recovered from independent pairwise constraints, which is why this is a first-class class with a group-preserving repair scope.
Boundeda metric must stay within a numerical or categorical bound (PEX coupling, IR drop, EM margin, match delta).
Softoptimized only after every hard and bounded gate passes.
Unsupportednot expressible with current coverage; must be refused or explicitly downgraded by policy.
ExternalOnlytrusted only after an external deck supplies evidence.
ManualReviewrequires human or foundry-note evidence before any signoff-quality claim.
These are evidence locations, not softness levels. A required ExternalOnly or ManualReview obligation blocks a signoff-quality claim until its evidence is attached. Do not conflate them with Soft.

Coverage — what the technology can check

Coverage is a nine-valued enum, never a boolean “supported”. A boolean collapses three distinct, dangerous situations — Approximate (a calibrated model that may be wrong by a known margin), ExternalOnly (correct only once a signoff deck runs), and ManualReview (a guideline a human must sign) — into one, and lets a layout look “fully supported” because the unsupported rules were simply never modeled. That is the single most common way to overclaim signoff readiness on a sparse PDK. 

Coverage =
  Coded | Partial | Approximate | ExternalOnly | ManualReview |
  RecommendedOnly | Unsupported | Missing | Contradictory

Crucially, coverage describes what the technology can check; class describes how the design must treat the obligation. They are orthogonal and must not be merged. A RecommendedOnly coverage (the PDK offers a rule but does not enforce it) is different from a Soft class (the design prefers but does not require a property); an ExternalOnly coverage (we have no internal check) is different from an ExternalOnly class (the obligation is trusted only after a deck runs).

Coverage forms an abstract domain ordered from Coded (most information) down to Missing/Contradictory (least / negative information). The merge of two views is the lattice meet: when views disagree or a value is unknown, the result moves toward Missing/Contradictory, never toward Coded. That conservative direction is the soundness condition that guarantees the certificate cannot certify a gap it failed to model. The merge and its MCMM keying live on the PDK Technology & Coverage page.

The constraint tuple

Every canonical constraint is a typed tuple. id is stable across deterministic recompilation; the remaining fields carry meaning, provenance, and evidence semantics. 

c = (id, scope, entities, predicate, class, bound, source,
     confidence, coverage, consumers, evidence, repair, waiver)
FieldRole
idcontent-addressed identity, c_<hex64> (see below).
scopeglobal, hierarchical, block-, device-, net-, terminal-, region-, or host-template-local.
entitiescanonical device / net / terminal / pin / region / layer / rule / analysis objects, sorted.
predicatea symbolic / typed function over layout state and evidence.
classone of the seven obligation classes.
bounda numerical or categorical limit, for Bounded obligations.
sourceprovenance: an authority + a stable source ID.
confidencefixed-point confidence — inference is statistical and can be wrong, so the graph records uncertainty rather than erasing it.
coveragethe nine-valued coverage.
consumerswhich of placement / routing / analysis / export / human-review must receive this obligation.
evidencethe evidence domains required before discharge (DRC, LVS, PEX, EM, …).
repairhow a violation is localized: group repair, single-device, net reroute, terminal-access regeneration, PDK gap, template conflict, or no auto-repair.
waiverNone, or a guarded, non-deleting waiver annotation.

Authority and waiver precedence

Contradiction handling needs an explicit trust order. Without one, a conflict between an inferred symmetry and a foundry mandatory rule has no principled resolution and gets settled by accident of iteration order. The default precedence, highest first: 

foundry mandatory rule or trusted signoff deck
  > host-template or package / shuttle contract
  > explicit user hard constraint
  > explicit user bounded constraint
  > generated primitive / library contract
  > inferred hard intent
  > inferred bounded or soft intent
  > heuristic repair preference

A waiver does not delete an obligation; it records an authority, scope, expiration/applicability condition, and evidence domain. Waiving a foundry or host-template hard rule is permitted only if the waiver authority is at least as high as the rule authority. The full admissibility rule is Invariant 2.

The canonical fact graph

Before any intent is compiled, fact extraction normalizes the schematic, hierarchy, devices, terminals, nets, host-template objects, fixed geometry, and prior-analysis snapshots into one canonical graph with sorted, stable names. Canonicalization — sorting hierarchy paths, normalized net names, and device terminal roles before any detector runs — is the precondition that makes the identity scheme below deterministic. If an input lacks stable names, the certificate marks deterministic replay as degraded rather than corrupting IDs.

The IntentGraph

All intent — user, inferred, PDK-derived, host-derived — is compiled into one typed IntentGraph, and every consumer reads projections of it. Using a single canonical graph is what makes “did routing honor the placer's intent?” a checkable set-equality rather than an unanswerable question: when placement and routing each re-infer intent from strings or geometry, they drift, and a repair correct for one breaks the other.

The graph carries, at minimum, these intent families:

  • primitive legality, device generation, terminal ordering, imported-cell equivalence;
  • symmetry, self-symmetry, hierarchical symmetry, ordering, alignment, proximity, spread, same-template, same-orientation;
  • matching, ratioed matching, interdigitation, common centroid, unit arrays, dummies, gradient-cancellation order;
  • current mirrors, cascodes, bias chains, signal/current flow, parallel current paths;
  • differential pairs, matched nets, length matching, parasitic matching, skew, paired terminal access;
  • sensitive / critical nets, shields, low-noise & high-impedance nodes, aggressor/victim budgets;
  • power, ground, clock, substrate, bulk, guard, tap, latch-up, isolation, deep-nwell, domain-crossing;
  • high-voltage, ESD, over-device routing, thick-metal, slotting, voltage-dependent spacing;
  • RF, inductors, transmission-line-like nets, passives, keepouts, substrate coupling, thermal;
  • host-template bindings, fixed pins, padframes, rails, wrappers, imported GDS, seal rings, export naming, reserved layers;
  • DRC, LVS, PEX, EM, ERC, antenna, density, fill, CMP, lithography, color, and manual-review obligations.

Deterministic, content-addressed identity

IDs are a hash of the obligation's semantic content, not of its discovery order. The compiler serializes an identity preimage from only the fields that define what the obligation means — class, scope, predicate, bound, source, coverage, consumer mask, repair policy, waiver, confidence, the sorted entity list, and the sorted required-evidence domains — then hashes it: 

id(c) = "c_" || hex64( H( canonical_preimage(c), seed ) )

canonical_preimage(c) = stable_serialize(
    class, scope, predicate, bound, source, coverage,
    consumers, repair, waiver, confidence,
    sort(entities), sort(evidence.required_domains))

Three properties make the scheme load-bearing:

  1. Position independence. Because the preimage is built from sorted sets and semantic fields rather than detector iteration order, two compilations that discover the same obligation in different orders produce the same ID. Identity is a function of meaning, not schedule.
  2. Collision-as-merge. Two detectors that infer the same obligation collide to the same ID by construction — the desired behavior: the obligation is deduplicated while its multiple provenances are recorded as evidence edges. Genuinely distinct obligations differ in at least one semantic field and hash apart.
  3. Seed separation. The tie-break seed participates in the preimage but is persisted in tuple metadata, never in the obligation payload, so re-seeding for adversarial-replay testing changes IDs predictably without altering semantics.

The reference build uses an FNV-1a 64-bit mixer; the production build substitutes a cryptographic digest (e.g. BLAKE3) so IDs are stable across architectures and resistant to accidental preimage collisions. The hash family is recorded in the certificate so replay detects a tool-version mismatch rather than silently comparing IDs from incompatible schemes. The same discipline names derived artifacts: contradiction cores hash their sorted member-ID list plus a reason tag (core_<hash>), so a core's identity is stable across runs and across the order conflicts were detected in.

Content addressing is a Merkle discipline

The scheme is an instance of content addressing — the same discipline that gives Git commits and IPFS objects their names. An object's name is the cryptographic hash of its own content; when an object references children, its hash covers its payload together with the children's hashes. A certificate that records the root hash of the obligation graph thereby commits to every obligation, core, and evidence edge beneath it: a replay that recomputes the root and gets a different value can localize the divergence by walking the DAG, turning the determinism claim into a constructive audit.

Symmetry-class canonicalization by color refinement

A subtle determinism hazard is symmetric structure: a differential pair or a current-mirror bank presents many structurally interchangeable devices, and a naive scheme would give their obligations IDs that depend on which device the detector visited first. The remedy is color refinement (the 1-dimensional Weisfeiler–Leman procedure): each vertex starts with a color from its intrinsic attributes (device type, model, terminal roles), then iterates — a vertex's new color is the hash of its old color paired with the multiset of neighbor colors — until two vertices share a color iff they are indistinguishable. Group members are canonicalized to their refined colors before the entity list is sorted and hashed, so a group obligation's ID is a function of structure, not iteration order.

Honest expressiveness bound. 1-WL is incomplete: there exist non-isomorphic graphs it cannot tell apart, and the message-passing GNN symmetry extractors are no more discriminating than 1-WL. The compiler therefore treats a color-refinement match as a strong structural hypothesis carrying a confidence, never as a proof of interchangeability — which is exactly why every inferred obligation carries provenance and confidence rather than a boolean.

Mapping the philis Constraint taxonomy

The current public API exposes a flat Constraint enum (crates/api/src/core.rs) with 22 variants, split by is_engine_supported() into 10 “engine-forwarded” and 12 “recognized but not yet honored”. In the target compiler these are user-declared inputs that get compiled into canonical tuples — each acquiring a class, a coverage, a consumer mask, and a content-addressed ID.

The realized API does not encode all seven canonical classes. Exactly as the placement vocabulary does, it encodes a four-member realized subset — IntentClass = Hard | Bounded | Soft | Unsupported — and Constraint::intent_class() is the mapping in code today. The Joint class folds into Hard with a group-preserving repair scope; ExternalOnly and ManualReview are carried by the coverage/evidence side, not by IntentClass. The table below gives both the realized IntentClass (what the code returns) and the richer canonical class (what the full model distinguishes).

The “Canonical class” column shows where each will land once the full compiler subsumes the realized subset (e.g. Matching and SymmetricGroup become true Joint obligations with group-preserving repair, rather than Bounded/Hard approximations).

The honesty bridge. The API's BuildWarning::UnsupportedConstraint (emitted in crates/api/src/builder.rs for the 12 not-yet-honored variants) is the API-level form of the compiler's inexpressibility contract: a consumer that cannot express an obligation must emit a linked skip, never drop it. When the full compiler lands, those warnings become certificate-visible ProjectedConstraintSkip entries keyed to a canonical ID — see Projection soundness. This is the same discipline the realized PlacementCertificate already follows: it emits a degraded certificate (every gate Degraded) rather than claiming a signoff it has not proven.
