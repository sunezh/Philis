Router API Mapping & Stubs

This page ties the signoff-first formulation to the concrete Philis surface — the philis crate (crates/api) — and states precisely what is real today versus a documented stub. The honesty rule from the API design rules applies verbatim: the one defect the design forbids is an API that accepts input it silently discards. Every stub below is shape-real and behavior-placeholder, and a stub result is marked degraded_confidence rather than passed off as signoff.

Where the router lives. Philis ships a single real crate, crates/api (package philis); the would-be crates/route, crates/place, and crates/constraints are empty scaffolds not yet in the workspace. The router therefore lives inside the façade: the typed contract is the module crates/api/src/core.rs, the stage oracle is core::run_routing, and the whole vocabulary is re-exported under the philis::router namespace (mirroring the eventual split into separate engine crates).

1. The typed contract

The formulation's public interface is geometry plus a certificate. In Philis: 

// the paper's RouteProblem / RouteSolution, as Philis types

RoutingRunInput   // the (stub) route problem fed to the oracle
RoutingResult     // Philis's RouteSolution: geometry + certificate + quality + diagnostics
   ├─ routed_segments : usize          // geometry summary
   ├─ quality         : RouteQuality   // signoff/parasitic facts, reported directly
   ├─ certificate     : RouteCertificate
   └─ diagnostics     : Vec<RouteDiagnostic>

Each formulation symbol maps to a concrete type:

The hard vector is the spine

HardVector is the lexicographic acceptance relation made executable. as_priority() returns the six components in gate order, and lex_le() compares two candidates so the search loop can keep the lexicographically best verified state. This is the structural alternative to a scalar penalty: a nonzero hard component is a different feasibility class, and no soft improvement can reorder two candidates whose hard vectors differ. 

let clean = HardVector::default();          // feasible
assert!(clean.is_feasible());

let drc_fail = HardVector { drc_violations: 1, ..Default::default() };
assert!(clean.lex_le(&drc_fail));            // clean ranks ahead
assert!(!drc_fail.is_feasible());            // a different feasibility class

The certificate is auditable, not anecdotal

let result = philis::router::run_routing(&input);
let cert = &result.certificate;

cert.hard.is_feasible();      // are all hard levels met?
cert.is_signoff_clean();      // feasible AND not degraded-confidence?
cert.pdk_state;               // which PDK readiness state?
cert.coverage.count(Coverage::ExternalOnly);  // LVS-only + signoff-only rules
cert.infeasible_core;         // preserved unsat core on failure

2. Where intent comes from

The router consumes intent, it does not rediscover it from geometry. In Philis the constraint taxonomy (philis::Constraint) is the source: its analog-aware variants (Symmetric, Matching, SelfSymmetric, SymmetricGroup, GuardRing, NetShield, SetNetClass, …) lower into the formulation's IntentGraph and its NetClass/group relations:

Constraint variantLowers to
SetNetClassNetClass on the named net
Symmetric / SymmetricGroup / SelfSymmetricNetClass::DifferentialPair / SelfSymmetric + the group-preserving closure grp(.)
MatchingNetClass::MatchedArray / ExactMatch + matched-group rip-up closure
NetShieldshield reservation (sh[n,e]) for a Sensitive/RfMmwave net
GuardRingNetClass::GuardSubstrate connectivity + spacing obligations

Constraint variants the engine cannot yet honor are surfaced as BuildWarning::UnsupportedConstraint(kind) at build time — never dropped silently. That is the same honesty contract this page enforces for the router.

3. The verification seam

The formulation's in-loop signoff (DRC / LVS / PEX / ERC) maps onto philis::verify::{drc, lvs, pex, erc} and the Layout::{drc, lvs, pex, erc} methods. The tiered flow lets these run at any point — on a manual tier against the incrementally-built GDS, or on the automation result in memory — which is exactly the "checks are callable during candidate generation and repair" property §2.G requires. The certificate's drc_evidence / lvs_evidence fields are where a run records which form of proof (internal, external report hash, or counterexample) backs each gate.

5. Roadmap to de-stub the router

  1. Compile a real PDK into Coverage/PdkState and a rule oracle; promote FullSignoff/AbstractComplete only when evidence supports it.
  2. Build the terminal-access oracle (§6) and fail fast with DiagnosticClass::NoLegalAccess when a required terminal has no candidate.
  3. Implement the DRC-clean single-net router (exact-local engine), then the multi-net conflict graph and no-short constraints.
  4. Add LVS connectivity extraction in the loop (the route-state invariant of §2.B), recording the certifying mode per net.
  5. Add incremental PEX/IR/EM/noise scoring into RouteQuality and feed outliers back into repair.
  6. Add group routing for symmetry/matching/shielding (the group-preserving invariant), populating max_diff_pair_skew_nm / max_length_match_delta_nm.
  7. Add color/cut-mask/via-decomposition classes where PDK data supports them.
  8. Populate real Evidence and minimized infeasible_cores, then flip each row above and drop the degraded_confidence stub marker.

Each step closes a row in the ledger and removes a degraded-confidence marker — never a silently-ignored input. The hard vector and the certificate shape do not change as the engine lands; only their contents graduate from stub to proven.
