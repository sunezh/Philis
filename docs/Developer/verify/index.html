The Philis Verification Crate

Status: design reference. This section specifies the target contract for crates/verify (philis_verify), the shared verification library that provides DRC, LVS, and PEX predicates to both the placement and routing engines. Nothing here is implemented yet — see Implementation status.

The one-sentence thesis. DRC rule predicates, connectivity tracking, and parasitic extraction formulas are domain-neutral computation — they depend on geometry and technology parameters, not on whether the caller is placing devices or routing wires. The verify crate owns the predicates and types; the checking loops stay in the consumers.

Why unify DRC, LVS, and PEX in one crate?

Both the placement engine (crates/place) and the routing engine (crates/route) need verification infrastructure. Without a shared crate, each engine would re-implement the same rule predicates, the same violation types, and the same parasitic formulas — with inevitable divergence. A spacing rule that place checks one way and route checks another produces contradictory results that the constraint certificate cannot reconcile.

The unification is at the predicate level, not the loop level. Place and route have fundamentally different iteration patterns:

  • Place runs a broad-phase R-tree query to find device-pair candidates, then calls DRC predicates in a narrow-phase loop over each candidate pair. The iteration order is device-centric: every device pair within the influence radius is checked.
  • Route runs an incremental commit-time delta loop. When a wire segment is added or removed, route dilates its bounding box by r_max to form a DrcRegion, queries the spatial index for nearby geometry, and calls predicates on each candidate. The iteration is edit-centric: only geometry affected by the edit is re-checked.

These loops are domain-specific and must stay in their respective crates. What the verify crate provides is the pure functions that both loops call: given two rectangles and a rule parameter, return a violation or nothing. This separation ensures that the predicates are tested once, the violation types are defined once, and any predicate bug is fixed in one place.

Dependency graph

philis-geom ──┐

The verify crate depends on philis-geom for Rect, coordinate types, and spatial query interfaces, and on philis-tech for RuleSet, LayerId, and ExtractModel (sheet resistance, capacitance parameters, via tables). It does not depend on place or route — the dependency arrow is strictly upward.

DRC rule predicates

The DRC module provides fourteen rule predicates, each a pure function that takes geometry and rule parameters and returns Option<DrcViolation>. The caller is responsible for broad-phase filtering; predicates assume the candidate pair is plausible (i.e., within the influence radius).

The predicate catalogue

check_width one rect, layer, min_width min(width, height) ≥ min_width
check_enclosure outer rect, inner rect, layer, min_enclosure All four sides' enclosure ≥ min_enclosure
check_area one rect, layer, min_area rect.area() ≥ min_area
check_eol_spacing two rects, layer, eol_width, eol_space, eol_within Enlarged spacing near end-of-line edges
check_prl_spacing two rects, layer, prl_threshold, prl_spacing Enlarged spacing when parallel run length ≥ threshold
check_overlap two rects, layer, same_net No intersection area when different-net
check_cut_spacing two via cut rects, cut layer, min_cut_spacing Edge-to-edge distance between cuts
check_same_net_notch two rects (same net), layer, min_notch_width, max_notch_length No narrow channel between same-net shapes
check_grid_snap one rect, layer, grid_pitch All edge coordinates are multiples of grid_pitch
check_well_spacing two well rects, well layer, min_well_spacing Well-to-well distance

check_outline_exceed one rect, cell boundary, layer Shape lies entirely within the cell boundary

Predicate invariants

Every predicate satisfies these invariants, tested by property-based fuzzing:

  • Symmetry. For two-shape predicates, check_*(a, b, ...) == check_*(b, a, ...). The order of arguments does not affect the result.
  • Orthogonality. check_spacing never fires on overlapping shapes (that is check_overlap's job). check_overlap never fires on same-net shapes (those are merged). Each predicate owns exactly one failure mode.
  • Determinism. Same inputs always produce the same output. No internal state, no randomness, no floating-point dependence in the decision (all comparisons are integer nm).
  • Complete metadata. Every returned DrcViolation carries the rule ID, layer, both shape references, the violation region (for UI highlighting), the required value, and the actual measured value. The consumer never needs to re-derive this information.

The ViolationKind taxonomy

All DRC violations are classified by a closed 14-variant enum. This taxonomy is shared across place and route, ensuring that violation counts, coverage tracking, and certificate reporting use the same vocabulary. 

pub enum ViolationKind {
    Overlap,          // different-net shapes intersect
    Spacing,          // edge-to-edge distance too small
    Width,            // shape narrower than min width
    Enclosure,        // outer shape does not extend far enough
    Area,             // shape area below minimum
    EOL,              // end-of-line enlarged spacing
    PRL,              // parallel-run-length dependent spacing
    CutSpacing,       // via cut-to-cut spacing
    SameNetNotch,     // narrow notch between same-net shapes
    GridSnap,         // edge not on manufacturing grid
    OutlineExceed,    // shape outside cell boundary
    WellSpacing,      // well-to-well distance
    WellEnclosure,    // well enclosure of diffusion
    ImplantSpacing,   // implant-to-implant distance
}

The DrcViolation type

Each violation carries full diagnostic metadata: 

pub struct DrcViolation {
    pub kind: ViolationKind,    // which rule category
    pub rule: RuleId,           // tech-model rule identifier (e.g., "M1.S.1")
    pub layer: LayerId,         // layer where the violation occurs
    pub shapes: (ShapeRef, Option<ShapeRef>),  // involved shapes
    pub region: Rect,           // bounding box for highlighting
    pub required: i64,          // the rule's required value (nm)
    pub actual: i64,            // the measured value (nm)
    pub same_net: bool,         // whether the shapes share a net
}

The shapes tuple uses Option for the second element because single-shape violations (Width, Area, GridSnap, OutlineExceed) involve only one shape. ShapeRef is an opaque 64-bit identifier that the caller maps back to its geometry store — the verify crate never owns or indexes geometry.

Bounded-influence incremental model

DRC checking is expensive if done from scratch on every edit. The verify crate supports an incremental model based on bounded influence: a modification to shape S can only create or resolve violations with shapes within distance r_max of S, where r_max is the maximum rule distance in the technology.

Influence radius

/// r_max = max(all spacing rules, all EOL within distances,
///              all enclosure rules, all well spacings,
///              all implant spacings)
pub fn compute_r_max(rules: &RuleSet) -> i64;

The consumer computes r_max once per technology and caches it. For SKY130, typical r_max values are in the range 200–500 nm.

DrcRegion and DrcDelta

When a shape is modified, the consumer constructs a DrcRegion — the shape's bounding box dilated by r_max — and queries its spatial index for all geometry within that region. The narrow-phase predicates run only on those candidates, producing a DrcDelta: the set of violations added and removed by the edit. 

pub struct DrcRegion {
    pub origin: Rect,    // original shape bbox
    pub dilated: Rect,   // origin expanded by r_max on all sides
    pub r_max: i64,
}

pub struct DrcDelta {
    pub added: Vec<DrcViolation>,    // new violations
    pub removed: Vec<DrcViolation>,  // resolved violations
}

This model is correct because DRC predicates are local: a spacing violation between shapes A and B depends only on A, B, and the rule parameters — not on any other shape in the design. The influence radius bounds the region where locality holds, and the DrcDelta captures the full effect of the edit on the violation set.

Place vs. route usage. Place typically runs DRC in batch mode (check all device pairs after a placement move) and uses DrcRegion to scope the batch. Route uses the incremental model directly: every wire commit produces a DrcDelta, and the running violation count is maintained as a prefix sum of deltas. Both patterns use the same DrcRegion and DrcDelta types.

LVS connectivity extraction via union-find

The LVS module provides a ConnectivityTracker — a union-find data structure augmented with net labels — and a connectivity extraction function that builds the tracker from layout geometry.

ConnectivityTracker

Each geometric element (terminal, shape endpoint, via landing) is an element in the union-find. Elements are grouped into components by geometric overlap: if two shapes on the same layer overlap or touch, their elements are unioned. Vias union elements on their upper and lower layers. Net labels propagate through unions. 

pub struct ConnectivityTracker {
    parent: Vec<u32>,
    rank: Vec<u8>,
    labels: Vec<Option<NetId>>,
    count: u32,
}

impl ConnectivityTracker {
    pub fn new(n: u32) -> Self;
    pub fn label(&mut self, x: u32, net: NetId);
    pub fn union(&mut self, x: u32, y: u32) -> UnionResult;
    pub fn find(&mut self, x: u32) -> u32;
    pub fn same_component(&mut self, x: u32, y: u32) -> bool;
    pub fn component_net(&mut self, x: u32) -> Option<NetId>;
    pub fn invariant_check(&mut self) -> Vec<LvsError>;
}

Union results and error detection

The union operation returns a three-variant result:

  • AlreadySame — both elements were already in the same component. No change.
  • Merged — two components with compatible labels (or at least one unlabeled) were merged successfully.
  • Short — two components with different net labels were merged. This is an LVS short circuit. The merge still happens (so that subsequent connectivity analysis is correct), but the short is recorded.

The invariant_check method scans all elements and reports two error classes:

  • Opens: elements with the same net label exist in different components. The schematic says they should be connected, but the layout does not connect them.
  • Shorts: elements with different net labels exist in the same component. The layout connects nets that should be electrically isolated.

LvsResult

pub struct LvsResult {
    pub opens: Vec<LvsOpen>,
    pub shorts: Vec<LvsShort>,
    pub mismatches: Vec<LvsMismatch>,
}

pub struct LvsOpen {
    pub net: NetId,
    pub components: Vec<Vec<u32>>,  // disconnected groups
}

pub struct LvsShort {
    pub nets: Vec<NetId>,      // the incorrectly merged nets
    pub component: u32,         // the representative element
}

Connectivity extraction algorithm

The extract_connectivity function builds a ConnectivityTracker from layout geometry in three passes:

  1. Same-layer overlap pass. For each layer, find all pairs of shapes that overlap or touch and union them.
  2. Via pass. For each via, find the shapes on the upper and lower layers that the via cuts land on and union them.
  3. Label pass. Assign net labels from port and pin shapes, then run invariant_check to detect opens and shorts.

PEX lumped-element surrogate

The PEX module provides first-order parasitic extraction: lumped resistance, ground capacitance, coupling capacitance, and via resistance per net. These are surrogate estimates, not signoff-accurate extraction — their purpose is to drive placement and routing quality metrics and repair loops. The constraint certificate records them as approximate evidence; true signoff requires an external extraction tool.

Parasitic formulas

ParasiticFormulaParameters from tech
Wire resistance R = (length / width) * sheet_r sheet_r: ohms/square per layer
Ground capacitance Cg = L*W*area_cap + 2*L*fringe_cap area_cap (fF/um²), fringe_cap (fF/um)
Same-layer coupling Cc = prl * coupling_cap(layer, spacing) coupling_cap: lookup table from ExtractModel
Interlayer coupling Cc = overlap_area * interlayer_cap interlayer_cap (fF/um²)
Via resistance Rvia = r_per_cut / num_cuts r_per_cut: ohms per single via cut

Accuracy expectations

The lumped-element model is intentionally simple. It captures the dominant parasitics — wire resistance scales with length/width, ground capacitance scales with area, coupling scales with parallel run length — without attempting to model fringing fields, corner effects, or process variation. Typical accuracy relative to a calibrated extraction tool:

  • Wire resistance: within 5–10% for straight segments (no bends).
  • Ground capacitance: within 10–20% (fringe cap approximation).
  • Coupling capacitance: within 20–40% (spacing-dependent lookup, no 3D field solving).
  • Via resistance: within 5% (direct lookup, well-characterized by foundry).

This is sufficient for ranking layout candidates, detecting outliers, and flagging matched-group parasitic deltas. It is not sufficient for signoff. The constraint certificate distinguishes between internal (approximate) and external (calibrated) extraction evidence.

NetParasitics and incremental update

pub struct NetParasitics {
    pub total_r: f64,       // total wire resistance (ohms)
    pub total_cg: f64,      // total ground capacitance (fF)
    pub total_cc: f64,      // total coupling capacitance (fF)
    pub total_rvia: f64,    // total via resistance (ohms)
    pub segments: Vec<SegmentParasitics>,
}

impl NetParasitics {
    pub fn add_segment(&mut self, seg: SegmentParasitics);
    pub fn remove_segment(&mut self, shape: ShapeRef);
    pub fn recompute_totals(&mut self);
}

The incremental interface allows the routing engine to maintain running parasitic totals across commit/rollback cycles without recomputing from scratch. After a batch of incremental updates, recompute_totals eliminates floating-point drift by re-summing from the segment list.

PexOutlier detection

The detect_outliers function scans a set of NetParasitics and flags nets whose parasitics exceed absolute thresholds or whose parasitic deltas within a matched group exceed the group's budget. Outlier kinds:

  • HighResistance — total wire R exceeds threshold
  • HighCoupling — total coupling Cc exceeds threshold
  • HighGroundCap — total ground Cg exceeds threshold
  • HighViaResistance — total via R exceeds threshold
  • MatchedGroupDelta — parasitic difference between matched nets exceeds budget

EM, IR drop, and antenna checking

The EM module provides reliability and manufacturability checks that complement DRC and PEX:

Electromigration (EM)

Electromigration causes wire failure when current density exceeds the metal's limit over time. The check uses Black's equation simplified to a threshold comparison: 

J = I / (width * thickness)    // current density
if J > J_max && segment_length > blech_length:
    emit EmViolation

The Blech filter exempts short segments: below the Blech product length, back-stress prevents void nucleation regardless of current density. This avoids false violations on via landings and short jogs.

Static IR drop

The power/ground network is modeled as a resistive mesh. Wire segments become resistors (using wire_resistance), vias become resistors (using via_resistance), and device terminals are current sinks. The system solves the sparse linear system G * V = I to compute node voltages. The worst-case voltage drop is reported. 

pub struct IrDropResult {
    pub node_voltages: Vec<(u32, f64)>,
    pub worst_drop: f64,
    pub worst_node: u32,
    pub converged: bool,
}

The sparse linear solve may delegate to philis-solver for production use. For early development, a direct Cholesky or iterative CG solver within the verify crate is sufficient.

Antenna ratio

During fabrication, metal layers act as antennas that collect charge from plasma etching. If the metal area connected to a gate oxide is too large relative to the oxide area, the accumulated charge can damage the gate. The check is: 

ratio = metal_area / gate_oxide_area
if ratio > max_ratio:
    emit AntennaViolation

The check is cumulative per layer and runs bottom-up through the metal stack. Antenna violations are typically repaired by adding diode insertions or by re-routing to break the antenna path.

Violation type hierarchy

The verify crate defines four violation types, each serving a different verification domain:

TypeDomainKey fields
DrcViolation Design rule checking kind, rule, layer, shapes, region, required, actual
LvsResult (opens/shorts/mismatches) Layout vs. schematic net, components (opens), merged nets (shorts)
EmViolation Electromigration shape, layer, j_actual, j_max, ratio
AntennaViolation Antenna ratio net, layer, ratio, max_ratio, metal_area, gate_oxide_area

Additionally, PexOutlier flags parasitic values that exceed thresholds but is not a violation in the DRC sense — it is a quality metric that feeds the constraint certificate's bounded obligations.

All violation types are designed for the constraint certificate: each carries enough metadata to identify the violation uniquely (for deduplication and tracking across incremental runs), to locate it in the layout (for UI highlighting and repair scoping), and to compare it against the rule's requirement (for pass/fail determination).

Coverage tracking

The RuleFamilyCoverage tracker counts how many candidate pairs were checked and how many violations were found, partitioned by ViolationKind. This feeds two purposes:

  • Certificate completeness. The constraint certificate needs to know which rule families were actually exercised. A rule family with zero checks is a coverage gap — either the design has no geometry on that layer (benign) or the checking loop skipped it (a bug). The unchecked_families method returns the gaps.
  • Performance diagnostics. Knowing which rule families dominate the check count helps identify optimization targets (e.g., PRL checks are expensive and may benefit from tighter broad-phase filtering). 
pub struct RuleFamilyCoverage {
    pub checked: HashMap<ViolationKind, u64>,
    pub violations: HashMap<ViolationKind, u64>,
}

impl RuleFamilyCoverage {
    pub fn record_check(&mut self, kind: ViolationKind, violation: bool);
    pub fn total_checked(&self) -> u64;
    pub fn total_violations(&self) -> u64;
    pub fn unchecked_families(&self) -> Vec<ViolationKind>;
}

Consumer integration

The verify crate is consumed by two engines with different integration patterns:

Place: device-pair broad/narrow-phase loop

The placement engine maintains an R-tree spatial index of device bounding boxes. After each placement move (swap, shift, mirror), it queries the R-tree for all devices within r_max of the moved device and calls DRC predicates on each candidate pair. The predicates it calls depend on the layer types involved:

  • Device layers: check_spacing, check_overlap
  • Well layers: check_well_spacing, check_well_enclosure
  • Implant layers: check_implant_spacing
  • All layers: check_grid_snap, check_outline_exceed

Place also uses ConnectivityTracker for equivalence checking (verifying that a placement preserves the schematic's connectivity) and NetParasitics to estimate parasitic impact of device placement (wire length estimates from placement coordinates).

Route: incremental commit-time delta loop

The routing engine maintains a per-layer spatial index of wire segments and vias. When a segment is committed, route:

  1. Constructs a DrcRegion from the new segment's bounding box.
  2. Queries the spatial index for all geometry within the dilated region.
  3. Calls the full set of applicable predicates: check_spacing, check_eol_spacing, check_prl_spacing, check_width, check_enclosure (for via enclosure), check_cut_spacing, check_same_net_notch.
  4. Produces a DrcDelta that is merged into the running violation state.
  5. Updates NetParasitics incrementally (add the new segment's contribution).
  6. Updates ConnectivityTracker with the new connection.

On rollback, the reverse delta is applied: added violations become removed, and the segment's parasitic contribution is subtracted.

The predicate/loop boundary is load-bearing. Moving the checking loop into the verify crate would force it to own a spatial index, which means it would need to understand device vs. wire geometry, commit/rollback semantics, and domain-specific iteration orders. That couples the verification library to the engine's internal representation — exactly the entanglement that makes DRC bugs hard to find and fix. The predicate/loop split keeps the verify crate testable in isolation: hand it two rectangles and a rule, get a violation or not.

Implementation status

This is a formulation and contract. To stay honest about what exists:

SurfaceTodayTarget

Soundness boundary. The verify crate provides surrogate verification — first-order models sufficient for driving placement and routing quality loops. It does not replace foundry signoff DRC, LVS, or PEX tools. The constraint certificate distinguishes between internal (approximate) evidence from the verify crate and external (calibrated) evidence from signoff tools. A result is signoff-quality only if every required hard gate is satisfied by calibrated evidence. Internal evidence alone makes the result signoff-ready, not signoff-quality.
