The Philis Solver Abstraction

Status: design reference. This section specifies the target contract that crates/solver (philis-solver) is meant to fill. The crate today is an empty scaffold with trait definitions and a builtin exhaustive backend planned. See Implementation status.

The one-sentence thesis. The concrete solver backend is a deployment decision, not an architectural one. Consumer crates program against traits; the user picks the backend at compile time via cargo features.

Why formal solvers in an analog layout engine?

Analog place-and-route is not a heuristic-only domain. Several core subproblems in the Philis engine are fundamentally decision problems — questions with a yes/no answer that a formal solver can answer exactly, where a heuristic can only approximate. The three solver families the engine needs correspond to three kinds of decision problem:

Solver familyDecision problemWhere it appears in Philis
SAT (Boolean satisfiability) "Does there exist an assignment of Boolean variables that satisfies all clauses?" Pin-access compatible-subset selection (route), grouped escape topology enumeration (route), MUS/MCS extraction for contradiction cores (constraints)
ILP (Integer Linear Programming) "Does there exist an integer-valued assignment that satisfies all linear inequalities, and if so, what is the optimum?" Via/color/min-area legality in the exact-local routing engine, resource allocation in placement
SMT (Satisfiability Modulo Theories) "Does there exist an assignment that satisfies Boolean structure and theory constraints (arithmetic, bitvectors, arrays)?" Advanced reconciliation passes that reason over arithmetic spacing/width constraints (future)

The key insight is that these are not exotic tools bolted onto a layout engine as an afterthought. They are the natural formalization of questions the engine must answer anyway. When the route crate asks "is there a legal via assignment for this local region?", it is asking a SAT question. When the constraint crate asks "what is the smallest set of obligations that are jointly infeasible?", it is asking an MUS question. Making the solver explicit — rather than burying ad-hoc backtracking in each consumer — is what makes the answers sound and the implementations replaceable.

The hot-switchable backend pattern

Different users have different solver backends available. An academic user may have CaDiCaL (open-source, no license cost) but not CPLEX. An industry user may have CPLEX (commercial, high performance) but prefer not to depend on CaDiCaL. A CI environment may have neither and need a fallback.

Philis handles this with a pattern common in high-performance computing but rare in EDA: trait interfaces with feature-gated backends. 

// Consumer code (e.g., crates/constraints/src/reconcile.rs)
// Programs against the trait — never mentions a concrete backend.
fn find_contradiction_core(solver: &mut dyn SatSolver, obligations: &[Clause]) -> MusResult {
    extract_mus(solver, obligations, Some(10_000))
}

// Wiring code (e.g., crates/api/src/lib.rs)
// Picks the backend based on what's available.
#[cfg(feature = "cadical")]
let mut solver = CadicalSolver::new();

#[cfg(not(feature = "cadical"))]
let mut solver = ExhaustiveSatSolver::new();

The consumer crate never imports a backend directly. It depends on philis-solver and programs against dyn SatSolver or dyn IlpSolver. The top-level binary or integration test picks the concrete backend. This means:

  • Adding a new backend (e.g., Z3) requires zero changes to the consumer crates.
  • Removing a backend (e.g., dropping the CPLEX dependency for an open-source release) requires changing one feature flag, not rewriting solver call sites.
  • Testing can use the builtin exhaustive backend (no external dependencies) while production uses CaDiCaL or HiGHS.
Cargo features, not runtime plugins. Backend selection is a compile-time decision via cargo features, not a runtime plugin system. This is deliberate: solver FFI bindings involve unsafe code and C/C++ link dependencies that must be resolved at build time. A runtime plugin system would push these dependencies into the user's environment in ways that are hard to diagnose and impossible to type-check.

The SatSolver trait

The SatSolver trait is the engine's interface to any Boolean satisfiability solver. It models the incremental, assumption-based SAT paradigm — the same paradigm used by modern solvers like CaDiCaL, Glucose, and MiniSAT.

What SAT solving means for layout

A SAT solver answers the question: "given a set of Boolean clauses (disjunctions of literals), is there an assignment of variables that makes all clauses true simultaneously?" In the layout domain, the variables represent design choices and the clauses represent constraints:

  • Pin access selection (route crate). Each pin has several candidate access patterns (directions a wire can approach the pin). Each candidate is a Boolean variable. Geometric conflicts between candidates are encoded as clauses ("if pin A uses access pattern 2, then pin B cannot use access pattern 3"). The SAT solver finds a compatible subset — an assignment where every pin has exactly one access pattern and no two patterns conflict.
  • Escape topology enumeration (route crate). For a group of pins that must escape a region (e.g., a transistor array), the possible escape orderings and layer assignments are encoded as Boolean variables. The SAT solver enumerates all feasible topologies, or proves that none exist.
  • MUS extraction (constraints crate). The SAT solver is used incrementally under assumptions to identify which constraints participate in a proof of infeasibility. This is how the engine computes contradiction cores — see MUS/MCS extraction below.

Trait surface

pub trait SatSolver {
    fn new_var(&mut self) -> VarId;
    fn add_clause(&mut self, lits: &[Lit]);
    fn solve(&mut self) -> SolverStatus;
    fn solve_under_assumptions(&mut self, assumptions: &[Lit]) -> SolverStatus;
    fn model(&self) -> Option<&[bool]>;
    fn unsat_core(&self) -> Option<Vec<Lit>>;
    fn num_vars(&self) -> u32;
    fn num_clauses(&self) -> u64;
    fn set_timeout(&mut self, millis: Option<u64>);
}

Key design decisions:

  • solve_under_assumptions is required, not optional. Assumption-based incremental solving is the foundation of MUS extraction and is supported by every serious SAT solver. A backend that cannot do this is not useful to Philis.
  • unsat_core returns Option — some backends (the exhaustive enumerator) do not support core extraction. The MUS algorithm handles this gracefully by falling back to deletion-based extraction.
  • model is indexed by VarId — entry i is the assignment of VarId(i). This avoids the overhead of a HashMap for what is fundamentally a dense array lookup.

Supporting types

/// Opaque variable identifier. Internally a u32 index.
pub struct VarId(pub u32);

/// A literal: a variable with a polarity.
pub struct Lit { pub var: VarId, pub positive: bool }

/// Result of a solver invocation.
pub enum SolverStatus { Sat, Unsat, Unknown, Timeout }

The IlpSolver trait

The IlpSolver trait is the engine's interface to any Integer/Linear Programming solver. It models a standard LP/MIP interface: create variables with bounds and integrality constraints, add linear constraints, set an objective, and solve.

What ILP solving means for layout

An ILP solver answers the question: "given a set of linear inequalities over integer (or real) variables, is there a feasible assignment, and if so, what assignment optimizes a linear objective?" In the layout domain:

  • Via/color/min-area legality (route crate). The exact-local routing engine encodes via choices, metal coloring (for multi-patterning), and minimum-area fill requirements as ILP variables. The constraints are geometric legality rules. The objective is typically to minimize via count or total wire area. The ILP solver finds the optimal legal assignment or proves that no legal assignment exists.
  • Resource allocation (placement). Distributing devices across placement regions while respecting area, aspect ratio, and well-proximity constraints can be modeled as an ILP when the number of candidate regions is small.

Trait surface

pub trait IlpSolver {
    fn new_var(&mut self, lb: f64, ub: f64, obj_coeff: f64, is_integer: bool) -> IlpVarId;
    fn add_constraint(&mut self, lhs: &[(IlpVarId, f64)], sense: Sense, rhs: f64);
    fn set_objective(&mut self, dir: ObjDir, coeffs: &[(IlpVarId, f64)]);
    fn solve(&mut self) -> SolverStatus;
    fn solution(&self) -> Option<&[f64]>;
    fn objective_value(&self) -> Option<f64>;
    fn num_vars(&self) -> u32;
    fn num_constraints(&self) -> u32;
    fn set_timeout(&mut self, millis: Option<u64>);
}

MUS/MCS extraction and contradiction cores

MUS and MCS extraction are the bridge between formal solving and Philis's constraint reconciliation system. They answer two dual questions about an infeasible constraint set:

ConceptQuestionUse in Philis
MUS (Minimal Unsatisfiable Subset) "What is the smallest set of constraints that are jointly infeasible?" The contradiction core in the constraint certificate. A MUS tells the designer which obligations conflict and cannot be simultaneously honored.
MCS (Minimal Correction Set) "What is the smallest set of constraints whose removal restores feasibility?" Repair strategies in reconciliation. Each MCS is a candidate waiver set — removing those obligations makes the remaining set satisfiable.

The two are mathematically dual: every MUS is a minimal hitting set of the MCS family, and vice versa. The solver crate provides both because the constraint crate needs both: the MUS for the contradiction core (what is wrong) and the MCS for the repair strategy (how to fix it).

Why this matters for analog layout

In analog layout, constraint conflicts are expected, not exceptional. A user declares symmetry for a differential pair. A host template fixes output pins at locations that make the symmetry axis geometrically impossible. A PDK minimum spacing rule forces the symmetric devices apart by more than the template allows. These are three independently correct specifications that together are infeasible.

Without MUS extraction, the engine can only say "the constraint set is infeasible" — a useless diagnostic for a designer staring at 200 obligations. With MUS extraction, the engine can say "these three specific obligations are jointly infeasible" and present the minimal conflict core. With MCS enumeration, it can add "you can resolve this by waiving obligation A, or by waiving obligation B" — concrete repair strategies the designer can evaluate.

The deletion-based MUS algorithm

The solver crate implements a deletion-based MUS algorithm, which works as follows:

  1. Activate all soft clauses by adding assumption literals. Each soft clause C_i is guarded by an activation variable act_i: the clause [neg(act_i)] ++ C_i is added permanently, and activating clause i means assuming act_i = true.
  2. Check feasibility. If the formula is SAT with all soft clauses active, return Satisfiable — no MUS exists.
  3. For each soft clause in the current working set:
    • Tentatively remove it (deactivate its assumption).
    • Solve under the remaining assumptions.
    • If still UNSAT: the clause is redundant — keep it removed.
    • If SAT: the clause is necessary for the UNSAT proof — restore it.
  4. Budget check. If the solver call budget is exhausted before all clauses are tested, return Unknown with the current (possibly non-minimal) subset.
  5. The remaining clauses form the MUS.

The algorithm makes at most n solver calls (one per soft clause) and produces a guaranteed-minimal UNSAT subset. The budget parameter ensures it terminates predictably even on large instances where individual solver calls may be expensive.

MUS result type

pub enum MusResult {
    /// Guaranteed minimal UNSAT subset. Indices into the soft_clauses slice.
    Minimal(Vec<usize>),
    /// Budget exhausted. Possibly non-minimal UNSAT subset.
    Unknown(Vec<usize>),
    /// All soft clauses together are satisfiable — no MUS exists.
    Satisfiable,
}

Convenience builders

Many solver encoding patterns recur across consumer crates. Rather than having each consumer re-implement "at most one of these variables is true" (a pattern that appears in both pin-access selection and obligation exclusion), the solver crate provides reusable builder functions that add clauses to an existing SatSolver:

BuilderConstraintEncoding
at_most_one(solver, vars) At most one of vars is true Pairwise (n ≤ 5), sequential counter (n ≤ 20), commander (n > 20)
exactly_one(solver, vars) Exactly one of vars is true at_most_one + one disjunctive clause
at_most_k(solver, vars, k) At most k of vars are true Sequential counter (totalizer encoding)
at_least_k(solver, vars, k) At least k of vars are true Dual of at_most_k on negated variables
exactly_k(solver, vars, k) Exactly k of vars are true at_most_k + at_least_k
implication_chain(solver, vars) v[0] → v[1] → ... → v[n-1] One binary clause per implication
implies(solver, a, b) a → b Single clause [neg(a), pos(b)]

The at_most_one encoding selection is automatic based on variable count. The pairwise encoding is optimal for very small sets (it produces n(n-1)/2 binary clauses, which modern SAT solvers handle efficiently). The sequential counter encoding scales linearly in auxiliary variables and clauses. The commander encoding handles large sets by partitioning into groups.

The backend landscape

The solver crate ships with one always-available backend and supports additional backends behind cargo feature flags:

BackendFeature flagSolver typeWhen to use
ExhaustiveSatSolver (always available) SAT Small subproblems (<20 variables), testing. Enumerates all 2n assignments. No external dependencies.
CaDiCaL cadical SAT Production SAT solving. State-of-the-art CDCL solver. Supports incremental solving, assumptions, and UNSAT core extraction. Open-source (MIT).
HiGHS highs ILP / LP Production ILP solving. High-performance open-source LP/MIP solver. Handles the exact-local routing engine's via/color/area problems.
Z3 (future) z3 SMT Advanced reconciliation with theory constraints. Needed when constraint conflicts involve arithmetic (spacing + width bounds). Not in the initial build.
The exhaustive backend is for small problems only. It enumerates all 2n assignments, so it is exponential in the number of variables. For problems with more than 20 variables, it will either panic or return Unknown. Production code should enable the cadical feature for SAT problems and the highs feature for ILP problems.

Who consumes this crate

The constraints crate

The constraint compiler's reconciliation phase (phase four of the seven-phase pipeline) uses the solver crate for two operations:

  • MUS extraction — when the reconciled IntentGraph contains obligations that are jointly infeasible, the constraint crate calls extract_mus to compute the minimal contradiction core. This core is recorded in the ConstraintCertificate with an explicit minimality tag and the algorithm that produced it (formal invariant #3: contradiction-core minimality).
  • MCS enumeration — for each contradiction core, the constraint crate calls enumerate_mcs to find all minimal repair strategies. Each MCS is a candidate waiver set that the authority-based resolution logic can evaluate.

The constraint crate also uses the solver crate's lowering surface for its quality comparator. The lexicographic objective (hard > bounded > soft) maps to a series of solver calls: first check hard feasibility (SAT), then optimize bounded metrics (ILP), then optimize soft metrics (ILP). The solver crate provides the traits; the constraint crate provides the lexicographic sequencing.

The route crate

The routing engine uses the solver crate in three contexts:

  • Pin access oracle. The access oracle selects a compatible subset of pin access patterns. Each pin has several candidate access directions; geometric conflicts between candidates are clauses. The SAT solver finds a conflict-free assignment. For small pin groups (<20 pins with <4 candidates each), the exhaustive backend suffices; for larger groups, CaDiCaL is used.
  • Exact-local engine. The exact-local router encodes via choices, metal coloring, and minimum-area fill as ILP variables. The ILP solver (HiGHS) finds the optimal legal assignment or proves infeasibility, triggering a rip-up and reroute.
  • Escape topology enumeration. For grouped pins (e.g., a transistor array's source/drain contacts), the possible escape orderings and layer assignments are encoded as a SAT formula. The solver enumerates all feasible topologies; the route crate picks the one that best satisfies the routing objective.
Why not just embed the solver in each consumer crate?

It seems natural for each consumer to manage its own solver dependency: the constraint crate pulls in CaDiCaL, the route crate pulls in HiGHS, and each manages its own FFI bindings. This is simpler in the short term but creates three problems that compound over time:

  1. Duplicated MUS/MCS code. Both the constraint crate and the route crate need MUS extraction — the constraint crate for contradiction cores, the route crate for diagnosing infeasible access patterns. Without a shared crate, each would implement its own deletion-based MUS algorithm, with its own bugs and its own performance characteristics. The MUS algorithm is non-trivial (budget gating, assumption management, incremental clause activation) and benefits from being written, tested, and optimized once.
  2. N copies of solver FFI bindings. CaDiCaL is a C++ library. Wrapping it in safe Rust requires unsafe blocks, lifetime management, and careful memory handling. Duplicating this wrapper in two crates doubles the surface area for memory safety bugs. A shared crate means one wrapper, one audit, one set of tests.
  3. No hot-switchable backends. If each consumer embeds its own solver, the user cannot switch backends without changing every consumer's dependency. With a shared crate, the user enables one feature flag and every consumer that uses dyn SatSolver gets the new backend. This is especially important for CI (where the exhaustive backend avoids external C++ dependencies) versus production (where CaDiCaL is needed for performance).

The cost of a shared crate is an additional node in the dependency graph and a trait-based indirection (dynamic dispatch via dyn SatSolver). The dynamic dispatch overhead is negligible compared to the cost of a single solver call (which involves search over an exponential space), and the dependency node is a pure leaf with no transitive dependencies of its own (when no backends are enabled).

Encoding patterns in practice

To make the solver crate's role concrete, here is how a consumer would encode a real routing subproblem — pin-access selection for three pins with two access candidates each: 

use philis_solver::{SatSolver, ExhaustiveSatSolver, Lit, VarId, SolverStatus};
use philis_solver::builders::{exactly_one};

let mut solver = ExhaustiveSatSolver::new();

// Each pin has two candidate access patterns.
// Variables: pin0_a, pin0_b, pin1_a, pin1_b, pin2_a, pin2_b
let vars: Vec<VarId> = (0..6).map(|_| solver.new_var()).collect();

// Exactly one access pattern per pin.
exactly_one(&mut solver, &[vars[0], vars[1]]);
exactly_one(&mut solver, &[vars[2], vars[3]]);
exactly_one(&mut solver, &[vars[4], vars[5]]);

// Conflict: pin0_a and pin1_b cannot coexist (geometric overlap).
solver.add_clause(&[Lit::neg(vars[0]), Lit::neg(vars[3])]);

// Conflict: pin1_a and pin2_a cannot coexist.
solver.add_clause(&[Lit::neg(vars[2]), Lit::neg(vars[4])]);

match solver.solve() {
    SolverStatus::Sat => {
        let model = solver.model().unwrap();
        // model[i] tells us which access pattern each pin uses.
    }
    SolverStatus::Unsat => {
        // No compatible access assignment exists — need to rethink
        // pin placement or add more access candidates.
    }
    _ => { /* timeout or unknown */ }
}

Soundness boundary. The solver crate provides interfaces and algorithms — it does not make correctness claims about the layout. A SAT result of Sat means the Boolean encoding is satisfiable, not that the physical layout is legal. The consumer crate is responsible for encoding the problem correctly. The solver crate's contract is: given a correct encoding, the solver returns a correct answer (or Unknown/Timeout if it cannot determine one). Bugs in the encoding are consumer bugs, not solver bugs.
